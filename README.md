# Rollcall QR Attendance

A compact, server-validated QR attendance system using Google Sheets as storage.

## What is included

- Multiple independent admin accounts stored in SQLite, with email OTP verification and password recovery.
- Student check-in with name and batch plus an optional email address for attendance updates.
- The first browser/device used for a student's attendance is linked to that student and can be reused for other subjects; another device is rejected.
- Server-side course mapping, Asia/Kolkata date/time, validation, duplicate protection, and signed 30-minute QR sessions.
- Ten subject tabs, a roster-driven absent finalization action, and a synchronized `Percentage` tab.
- Subject sheets show one consecutive date column per day from the first recorded date through today, newest first. Sundays and configured holidays are marked `Holiday`. Other dates with no attendance remain blank; when attendance is finalized for a class day, unmarked roster cells become `Absent`. Blank dates and holidays are excluded from attendance totals and percentages.
- Responsive instructor dashboard and mobile-first student page.
- Successful user actions show an accessible green notification at the top of the page that dismisses after five seconds.

## 1. Create the Google spreadsheet

Create one spreadsheet and add these tabs exactly:

- `Students`
- `Percentage`
- `Subject 1` through `Subject 10`

Use these headers in `Students`:

```text
Student ID | Student Name | Batch | Email
```

The app automatically adds a new student to this tab the first time that student marks attendance. The `Student ID` is generated by a Google Sheets formula, not by the server. Existing students are matched by name and batch, so duplicate roster rows are not created. The app adds an optional `Email` column to the roster; emails are used only for notifications and summaries. Subject tabs continue to use their existing attendance layout. Only P1-P10, J1-J10, and D1-D10 are accepted. Use these headers in every subject tab:

```text
Date | Time | Student Name | Batch | Course | Subject | Status | Attendance Source | Session ID
```

Use these headers in `Percentage`:

```text
Student Name | Batch | Course | Subject | Attended Classes | Total Classes | Subject Percentage | Full-Course / Overall Percentage
```

Share the spreadsheet with the Google service-account email as **Editor**, then copy the spreadsheet ID from its URL.

## 2. Configure and run

```powershell
Copy-Item .env.example .env
```

Edit `.env`:

- `JWT_SECRET`: a random secret of at least 32 characters used to sign session cookies. Required in production; local development generates an ephemeral value if omitted.
- `DATABASE_URL`: SQLite database file path; defaults to `./data/attendance.sqlite`. Keep the data directory on persistent storage where available. Render Free uses temporary storage, so its SQLite data may be lost after a restart or redeployment.
- `DEVICE_LOCKS_PATH`: optional JSON path for legacy migration and per-session locks. Keep it on persistent storage where available (for example `/var/data/.device-locks.json` on a host with a disk); Render Free uses `/tmp/attendance-data/.device-locks.json`, which is temporary. Active student-device ownership is stored in the SQLite database.
- `TRUST_PROXY_HOPS`: number of trusted reverse-proxy hops used to determine `req.ip`; defaults to `1` in production and `0` locally. Render sets it to `1`; do not raise it unless the deployment's proxy chain requires it.
- `EMAIL_PROVIDER`: select `resend` for Resend's HTTPS API or `smtp` for SMTP; defaults to `smtp` for existing deployments.
- `EMAIL_FROM`: required sender email address. Resend requires an address on a domain verified in Resend. Outgoing email displays "Attendance Management System" as the sender name.
- `RESEND_API_KEY`: required when `EMAIL_PROVIDER=resend`; keep it private and configure it only in the server environment.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`: required when `EMAIL_PROVIDER=smtp`. `SMTP_USER` is the sender account, not an admin identity. SMTP uses `EMAIL_FROM`; `SMTP_FROM` remains supported as a backwards-compatible fallback. Use your provider's app password. The app logs a clear warning if the selected email provider is not configured; credentials remain server-side.
- `GOOGLE_SPREADSHEET_ID`: spreadsheet ID.
- `GOOGLE_SERVICE_ACCOUNT_JSON`: the full service-account JSON on one line (for Render, enter it as one value). Locally, prefer `GOOGLE_SERVICE_ACCOUNT_FILE` with the path to the JSON key file; never commit the key file. For compatibility, the JSON setting also accepts a local file path.
- `APP_URL`: the URL used in QR codes. For local phone scanning, keep the phone and computer on the same Wi-Fi network; if `APP_URL` is `localhost`, the app automatically substitutes the computer's LAN IPv4 address. For scanning from another network, set this to the app's public HTTPS URL.
- `MIN_ATTENDANCE_PERCENTAGE`: optional minimum threshold for the student attendance warning. Defaults to `75`.

Generate a private value for `JWT_SECRET` with:

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Put the generated value in `.env` as `JWT_SECRET`. Do not share or commit it.

For Resend, set `EMAIL_PROVIDER=resend`, `RESEND_API_KEY` to the API key, and `EMAIL_FROM` to a sender address on a domain verified in Resend. For Gmail SMTP, set `EMAIL_PROVIDER=smtp`, enable 2-Step Verification on the sender account, and create an App Password. Set `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=465`, `SMTP_SECURE=true`, `SMTP_USER` to the sender account, `EMAIL_FROM` to its sender address, and `SMTP_PASSWORD` to the App Password. Gmail also supports submission on port 587 with `SMTP_SECURE=false` (STARTTLS). For other SMTP providers, use their host, port, TLS mode, and sender credentials. Do not use the administrator or student's email as the SMTP login.

To create a structure-only copy before moving the app to a new Google Spreadsheet file:

```powershell
$env:SOURCE_GOOGLE_SPREADSHEET_ID = "current-spreadsheet-id"
$env:NEW_SPREADSHEET_NAME = "Rollcall Attendance Copy"
npm run migrate:sheet
```

The command creates a native Google Sheets copy, preserving tabs, colors, formulas, filters, validations, column widths, and formatting. It clears all rows below the first row, so old attendance records and roster data are not carried over. Copy the new ID printed by the command into `GOOGLE_SPREADSHEET_ID`, then restart the app. The service account must have access to the source spreadsheet and permission to create a copy in Google Drive.

Then run:

```powershell
npm install
npm start
```

The default port is `3000`. If you see `EADDRINUSE`, the app is already running on that port; use `http://localhost:3000` instead of starting a second copy. To run another copy, set a different port in the same PowerShell window:

```powershell
$env:PORT = "3001"
npm start
```

Open `http://localhost:3001`. To stop a running app, press `Ctrl+C` in the terminal where that app was started. `npm run start:clean` checks whether the port is occupied and reports the listener without terminating it.

Startup batches subject-sheet reads to reduce Google Sheets API quota usage. If Google reports a read-quota limit, the app retries with increasing delays; after repeated recent restarts, wait about a minute for the per-minute quota window to reset, then restart the app once.

Run the authentication integration/security checks with `npm test`.

Open `http://localhost:3000`. For a phone-accessible QR without changing Windows Firewall settings or requiring the phone to be on the same Wi-Fi, install Cloudflare Tunnel once:

```powershell
winget install --id Cloudflare.cloudflared
```

Then start the temporary public tunnel:

```powershell
npm run start:tunnel
```

The command starts both the tunnel and a fresh attendance app process with the temporary HTTPS URL configured for QR generation. If port 3000 is already in use, stop the app in its original terminal by pressing `Ctrl+C` there, then run `npm run start:tunnel` again; do not tunnel to the old app process, because it may still generate QR codes with its old local URL. Keep the tunnel terminal and computer running while students check in; press `Ctrl+C` to stop both. Open the printed HTTPS URL in your browser, sign in, and generate a fresh QR. The temporary URL changes when you restart the tunnel, so generate a new QR each time. Active attendance sessions are held in memory and do not survive an app restart. This tunnel is for development/classroom use; for a permanent address, deploy the app to a public HTTPS host and set `APP_URL` to that address. To keep the QR limited to the local network instead, use `npm start` and connect the phone to the same non-guest Wi-Fi; firewall or router settings may still prevent local access.

Administrator access has two effective roles. The singleton `MAIN_ADMIN` assignment is kept in SQLite; all other accounts remain `ADMIN`. A new admin can register from the login page using their name, email, phone number, and a password they choose. Their email must still be verified by OTP, and they cannot log in until the Main Admin approves them. The Main Admin can approve a pending registration directly from its row in the Admin Accounts table using **Give Access**; this grants all currently configured subjects. If a valid verification OTP was already sent during registration, approval reuses it rather than invalidating it with another code. If no valid code remains, approval sends a new one. Approval can precede OTP verification, but the account remains inactive until OTP succeeds. If email delivery fails, the dashboard reports that separately and the Main Admin can retry using **Resend verification OTP** once the resend cooldown passes. The separate pending-registration queue is not required for this action. The Main Admin can also invite an admin from Admin Management and select subjects for that invitation. The invite email contains a temporary password formed from up to eight characters of the admin's first name plus three random digits, along with a one-time code; the invitee must use both to sign in and choose a permanent password before using the dashboard. Resending creates a different temporary password. Main Admin-only APIs enforce approval, account status, and subject assignments on the server; client-supplied roles are never trusted. Deactivation/removal immediately invalidates sessions, and already-issued QR sessions stop working if their issuing admin is deactivated or loses access to that subject. Removed admins are hidden from the Admin Accounts dashboard; removal erases their personal account fields, password hash, active sessions, subject assignments, and login history from SQLite and anonymizes their account/audit references. The event timeline and actor/target IDs remain for auditability. Existing regular admins retain access to all configured subjects after the additive migration; the Main Admin always retains access to every configured subject.

The SQLite database is authoritative for admin phone numbers, verification and approval state, account status, audit history, and subject assignments. These security-critical values are not stored in Google Sheets. The migration adds columns and tables without removing or rewriting attendance data. On startup, previously removed admin accounts are also anonymized and their sessions, credentials, OTPs, subject assignments, and login metadata are erased; account and audit worksheets are updated to remove their old personal details. Before upgrading an existing version 1–6 database, startup also creates a timestamped `.pre-v7-...bak` SQLite copy beside the database; keep an independent backup before deploying as well.

Set `MAIN_ADMIN_BOOTSTRAP_SECRET` to a separate random value of at least 32 characters in the environment (never commit it or put it in Sheets). On a new database, use **Set up Main Admin**, provide that secret, create a password, and verify the email OTP. On an existing database without a designated Main Admin, **Claim Main Admin** claims an existing verified, active admin account and requires its existing email/password and the bootstrap secret; it does not create a second account. The claim is stored atomically in SQLite and cannot be repeated. The environment secret can then be rotated or removed; it is only needed while no Main Admin is designated. Public registration can create only a pending regular-admin request; it cannot create the first Main Admin or promote an account. Every registered admin needs Main Admin approval before sign-in.

### Main Admin recovery

`node scripts/reset-main-admin.js --backup-only` creates and verifies a full SQLite backup without changing records. It requires the configured `MAIN_ADMIN_BOOTSTRAP_SECRET` and asks for it in a protected interactive terminal, never as a command-line argument. Securely copy this backup off the Render instance before proceeding. Next, run `node scripts/reset-main-admin.js --dry-run` to review the current assignment and verify that at least one verified, active, approved admin can claim it; dry-run is also the default. Only after reviewing the report and securing the independent backup should an authorized operator explicitly run `node scripts/reset-main-admin.js --apply`. Apply mode creates another fresh backup beside the configured database, then clears only `main_admin_config.admin_id` and `created_at`. It does not delete or disable admin accounts, OTPs, sessions, audit rows, device records, attendance, subjects, or spreadsheet data. The reset is safe to repeat.

This procedure does not repair a forgotten password, an unverified/inactive account, or broken email delivery. Recover those first through the existing password-reset/OTP and email-provider configuration. The generated SQLite backup is only an additional local rollback point: copy it to secure storage outside the Render instance before restarting or redeploying. On Render Free, both the live SQLite file and the backup under `/tmp` are ephemeral and may disappear; do not treat either as a permanent backup. To roll back before that happens, stop the service and restore the backup over the SQLite database, then restart. No production reset is run by deployment or application startup.

### Explicit reset of all administrator access

Use `node scripts/reset-admin-accounts.js` only when all admin credentials must be revoked and a new Main Admin must be initialized. This is a separate, operator-run CLI; it is not called during startup or deployment. It requires the configured `MAIN_ADMIN_BOOTSTRAP_SECRET` and reads it from a protected interactive terminal rather than accepting it as a command-line argument. It refuses to operate on an unexpected schema or a database with foreign-key violations.

First stop or suspend the application during a maintenance window so no user can register or authenticate while the reset is being prepared. Run the default dry-run and review the counts before proceeding:

```text
node scripts/reset-admin-accounts.js --dry-run
node scripts/reset-admin-accounts.js --backup-only
```

Copy the backup reported by `--backup-only` to secure durable storage outside the Render instance and verify that it is retained there. Only then, after an authorized operator explicitly approves the displayed impact, apply the reset:

```text
node scripts/reset-admin-accounts.js --apply
```

Apply mode makes a fresh SQLite online backup beside the database, validates its integrity and foreign keys, then runs the reset transaction. Admin rows are retained as anonymized tombstones so audit and foreign-key references remain valid; credentials, sessions, OTP challenges, and subject assignments are revoked. Main Admin assignment is cleared, access-request details tied to these accounts are anonymized, and identifying text in their audit events is redacted while the audit events themselves remain. Student, attendance, subject, device-registry, legacy device-lock, and unrelated database rows are preserved. The utility does not connect to Google Sheets or modify any spreadsheet. Its dry-run and backup modes do not change database rows, and rerunning apply is safe.

After applying the reset, restart the application and use **Set up Main Admin** with a new password and the bootstrap secret. The setup page now permits creation when no verified, active, approved admin can claim the assignment, even if anonymized admin tombstones remain. The Main Admin account is not usable until its verification OTP is successfully delivered and accepted. If delivery fails, setup is rolled back and can be retried; fix the email provider first rather than bypassing verification. Then create regular admins through the normal signup/invitation flow and verify/approve them as usual. The bootstrap remains one-time and duplicate Main Admin setup is rejected.

This operation revokes every admin account, including any otherwise recoverable account, and anonymizes its email/phone/profile fields. Prefer the narrower `reset-main-admin.js` claim-recovery procedure above when an existing verified account can safely become Main Admin. Do not perform the all-admin reset just to resolve email-delivery or Google Sheets errors. The reset does not repair either integration, and a 10-column sheet with an unknown header order continues to be skipped safely. Local tests exercise only temporary databases and mocked mail; they do not verify production email configuration or authorize a production reset.

For Render Free, configure `DATABASE_URL=/tmp/attendance-data/attendance.sqlite` and `DEVICE_LOCKS_PATH=/tmp/attendance-data/.device-locks.json`; no persistent disk is required. These paths are temporary. Also configure `JWT_SECRET` (at least 32 random characters), `MAIN_ADMIN_BOOTSTRAP_SECRET` (a separate value of at least 32 characters), `EMAIL_PROVIDER=resend`, `EMAIL_FROM` on a domain verified with Resend, and `RESEND_API_KEY`. Configure `GOOGLE_SPREADSHEET_ID` and `GOOGLE_SERVICE_ACCOUNT_JSON` with the production spreadsheet ID and complete service-account JSON; do not use a local Windows file path on Render. SMTP remains optional when `EMAIL_PROVIDER=smtp`; provide `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD` (a Gmail App Password for Gmail), and a valid `EMAIL_FROM` or legacy `SMTP_FROM`.

Database migration v6 adds a `must_change_password` flag for one-time temporary credentials. It is additive and does not rebuild or delete existing accounts, attendance, device data, or legacy admin access-request rows. Migration v5 may have created a legacy access-request table, but the public request and review flows are no longer exposed or used. Migration v4 adds the singleton Main Admin assignment and status/removal timestamps and extends existing audit metadata. Existing `Admin Accounts` and `Admin Audit Log` worksheet headers are extended only when they exactly match the known older format; unexpected headers are not overwritten. SQLite remains authoritative for authorization and audit records.

Admin credentials, OTPs, bootstrap assignments, audit events, and persistent login sessions are stored in SQLite, never in Google Sheets. Passwords use bcrypt; OTPs are hashed, expire after 10 minutes, and allow at most five attempts. OTP requests have a one-minute resend cooldown and rate limits. Repeated admin login failures temporarily lock the account. Administrative actions record the actor ID/role, target ID, timestamp, action, result, and reason in the audit log. The Main Admin cannot be modified or removed through regular-admin management actions. The application imports a previous `.admin-account.json` account into SQLite on startup when present.

Device registrations are enforced by the same SQLite database. A browser/device identifier is generated randomly and only its SHA-256 hash is stored. One active device is allowed per student roster record, and one device cannot switch between students. A device-blocked check-in stays on the student QR page and shows the existing device-limit message; it does not redirect to the administrator login or bypass the device restriction. The dashboard links to a separate **Registered student devices** page at its bottom; all active admins can view the device details and device-only audit history or release an old registration after confirmation and a reason. If a student changes phones, release the old phone there so they can register the replacement on their next check-in. Main Admins have a separate **Admin logins & access** page for account management and admin-only login/access audit history; regular admins cannot access that page or its API. Legacy student-to-device locks are imported from the existing device-lock JSON file on startup. Google Sheets receives separate `Device Registry`, `Admin Accounts`, and `Admin Audit Log` tabs. The `Admin Accounts` report includes the admin name, email, role, status, join date, last login, and latest password-change date, but never the password or password hash. Add `Account Lock Status` and `Admin Name` as columns K and L, respectively, to existing 10-column Admin Accounts sheets to enable the complete current report. Current, known previous, and exact known legacy admin/audit headers are supported by mapping values to recognized header names without reordering or rewriting existing headers. Unknown layouts are diagnosed and skipped safely; populated data is never shifted beneath different headers. Missing headers are initialized only on otherwise-empty tabs. The database is authoritative if a reporting-sheet sync fails, and the UI reports sync failures.

The app records only the latest observed client IP address, derived from Express's configured proxy chain (not a browser-supplied IP field). It clears that address when a device is unlocked; device hashes and audit history remain in SQLite. Device identifiers live in browser storage and are not physical-device authentication: clearing storage, private browsing, another browser, or a copied token can change or imitate the browser identity. Student check-in still uses the existing roster name/batch workflow, so it cannot prove a person's real-world identity; review roster access and use the admin unlock process for legitimate recovery. Restrict access to the whole Google spreadsheet to trusted administrators because Google Sheets sharing permissions are file-wide and hiding/protecting a tab does not make its contents private from other spreadsheet editors.

Email is sent through one backend service with reusable, responsive HTML and plain-text versions for verification OTPs, invitations, welcome messages, password resets, account status changes, attendance alerts, and attendance summaries. Select Resend over its HTTPS API or SMTP using `EMAIL_PROVIDER`; invitations and verification require the selected provider to be configured. Students may enter an email during QR check-in; the address is saved in the Students sheet and used for present/absence notices. Failed attendance email delivery does not undo an already-recorded attendance event and is explicitly reported in the response/UI. From the dashboard, admins can send a summary to the roster email; counts are calculated from attendance records in the configured subject sheets. Never place email credentials in frontend variables.

## Attendance lifecycle

1. Instructor selects a subject, optional batch scope, and QR validity of 5, 10, 20, or 30 minutes, then generates a QR. The dashboard shows a countdown and automatically finalizes the session when that duration expires; the instructor can close it earlier.
2. The QR is accepted only until its signed session's server-side expiration time and cannot be edited without invalidating its signature.
3. Students submit a name, batch, and optionally an email for updates. The server maps the course and writes `Present`.
4. Instructor clicks **Close session and mark absences**. Students in the session scope without a mark receive `Absent` when attendance was recorded for that class. If nobody was marked, the date remains blank. Sundays and configured holidays cannot be used to record attendance and are excluded from totals.
5. The `Percentage` tab is rebuilt from present and absent rows. Blank dates and holidays do not count toward total classes.
6. After marking attendance, students can check their own subject attendance. The lookup uses the subject matrix date columns, excludes future dates, and matches by name plus batch.

Close a session only after the class is finished. Past records are not exposed through correction controls. Google Sheets itself should be restricted to trusted administrators.

The dashboard's **QR Session Recovery** section lists active and closed QR sessions managed by admins who still have access to their subject. An authorized admin can view the original QR or recover a fully closed session; recovery reuses its original URL, token, ID, and QR image, and keeps existing present/absence records. A student who was marked absent when the session closed can submit through the recovered QR to update that student's same-date absence to present; existing present records and device locks remain unchanged. Session recovery and the student/session state are held in the app's existing in-memory session store and are available only while the server process remains running. No attendance rows or QR sessions are restored from Google Sheets after a server restart.

The SQLite database (`DATABASE_URL`) contains the authoritative device registry, admin audit history, and admin authentication data. The existing `DEVICE_LOCKS_PATH` stores older per-session lock data and is also read once to migrate legacy student-device locks. Keep both paths on persistent storage where available and back them up. On Render Free, the configured `/tmp/attendance-data` paths are temporary; database contents, admin accounts and setup, device registrations, audit history, and lock files may be lost after a restart or redeployment.

## Deploy publicly on Render

The development address (for example, `192.168.x.x`) is private to your local network. To let phones on other networks scan attendance QR codes, deploy the app to a public HTTPS host. This repository includes a `render.yaml` blueprint for a Render Free web service. It stores SQLite and device-lock files under `/tmp/attendance-data` and does not request a persistent disk. Render Free storage is ephemeral: those files, including admin accounts, Main Admin setup, device registrations, and audit history in SQLite, may be lost after a restart or redeployment. Attendance records already written to Google Sheets remain there, but the app's local authorization and device state is not backed up by Sheets. Use this setup only if you accept that risk.

1. Push this repository to GitHub and create a new Blueprint on Render using that repository and its `render.yaml`.
2. During setup, provide `GOOGLE_SPREADSHEET_ID`, `GOOGLE_SERVICE_ACCOUNT_JSON`, and `MAIN_ADMIN_BOOTSTRAP_SECRET`. Generate the bootstrap value with a password manager or a cryptographically secure random generator; use at least 32 random characters and keep it separate from `JWT_SECRET`. The service account must have Editor access to the spreadsheet. In Render, enter the service-account JSON as one value; keep all secrets private.
3. In Render, set `EMAIL_PROVIDER=resend`, `EMAIL_FROM` to a sender address on a verified Resend domain, and `RESEND_API_KEY` to your private Resend API key. Alternatively, select `EMAIL_PROVIDER=smtp` and configure the SMTP variables. Wait for deployment, then open the service's public `https://<service-name>.onrender.com` URL and initialize/claim the single Main Admin using the bootstrap secret. Complete email verification for a newly created Main Admin.
4. If Render did not set `APP_URL`, it can be left unset: QR links use the incoming public host and HTTPS forwarded by Render. Alternatively set it to the exact public HTTPS service URL. Generate a fresh QR after deployment; QR sessions are held in memory and do not survive a service restart.
5. Keep the service to one running instance. This app uses in-memory active QR sessions and process-local rate limits. On Render Free, SQLite and per-session device locks are stored in temporary `/tmp/attendance-data`; do not rely on them as permanent storage.

For production hosts with persistent storage, keep `DATABASE_URL` and `DEVICE_LOCKS_PATH` on that storage. Render Free uses temporary storage for these paths, so local admin and device state can be lost. Use HTTPS, keep `JWT_SECRET` private, and configure `TRUST_PROXY_HOPS` to match the known proxy chain. Never commit `.env` or place service-account credentials in `public/`. The admin cookie is HttpOnly, SameSite=Strict, signed, and expires after eight hours.

## Smoke test checklist

- Initialize Main Admin using the configured bootstrap secret, verify the email OTP, then sign in and reject an incorrect password.
- Verify bootstrap rejects a wrong secret, succeeds once, and rejects a repeated claim; test claiming an existing verified admin on an existing database.
- Register a new admin with a phone number and verify that **Give Access** appears in that account's row. Approve it before OTP, verify it remains inactive, then complete OTP and confirm the account can log in.
- Approve a verified pending registration from its account row and verify the admin receives all configured subjects and can open a session for each one.
- Repeat Give Access and verify it does not create duplicate accounts or duplicate approval audit events.
- Confirm the admin-management page grants registered admins all configured subjects and the invitation flow applies its selected subjects.
- As Main Admin, invite a regular admin; verify its email and confirm login is still rejected while inactive, then activate it with a reason.
- As a regular admin, try the admin list, invitation, activation/deactivation, edit, recovery, and removal endpoints directly; each Main-Admin-only operation must return 403 and make no changes.
- Verify a regular admin cannot modify/remove the Main Admin, elevate any role, or deactivate itself; verify the Main Admin account cannot be deactivated or removed through management actions.
- Deactivate an active regular admin and verify its existing cookie fails on the next protected request; then exercise audited recovery and reactivation.
- Remove a regular admin and confirm sessions and subject access are revoked, personal details and login history are erased, and anonymized audit events remain.
- Reject duplicate email and phone registrations, wrong/expired OTPs, unverified login, pending-approval login, and deactivated admin login.
- Reject duplicate email signup, wrong/expired OTPs, unverified login, and deactivated admin login.
- Confirm API signup cannot set a role and unauthenticated admin management requests are rejected.
- Register Student A's device and mark attendance for that student in multiple subjects and dates; verify the same device is rejected for Student B and a second device is rejected for Student A.
- Send simultaneous registration attempts from one device for two students and verify exactly one owner is saved; restart the app and verify the lock remains.
- Verify unauthenticated requests cannot list device/audit records or unlock; as an admin, unlock with a reason and confirm the registry and audit entry.
- Confirm browser storage reset requires admin recovery and that the database remains authoritative if a Google registry/audit sheet sync fails.
- Reset the password with an email OTP and confirm the previous password no longer works.
- Generate a QR for a subject and submit a valid student.
- Submit the same student again and confirm the duplicate message.
- Try `Rahul123`, `Rahul@`, and `P11`; all must be rejected.
- Close a scoped session and verify missing roster students receive `Absent`; when roster emails and SMTP are configured, verify absence notifications.
- Enter a student email at check-in and verify the attendance confirmation arrives at that address. From the dashboard, send that student's summary and verify counts against the subject sheets.
- Add a student with an email to the roster, close a session where they were not present, and verify an absence email with the selected subject/date/faculty. `npm test` checks the dynamic HTML/text template values without requiring external SMTP credentials.
- Verify the Percentage tab reports `17 / 20 = 85.00%` for a 17-present, 3-absent case.
- Wait for or temporarily set `QR_MINUTES=1` and confirm expired QR submission is rejected.
